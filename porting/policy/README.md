# SELinux policy fragments for the boot image

> **Current state: CURRENT-STATE.md.** The entries below are the
> running log and are ordered newest first; the top entry is not
> necessarily the current state. Build, package and flash:
> [BUILD_TISSOT.md](../../BUILD_TISSOT.md).

Extra CIL appended to the ramdisk's `userdebug_plat_sepolicy.cil` by
`porting/logging/package-diag-boot.py --policy-append`. The policy is
compiled at boot, so a fragment changes what the ROM enforces without
touching `/system` or `/vendor`, both of which are read-only and dm-verity
protected.

`port-*.cil` are part of the port: `porting/tools/build-kernel.sh` appends
them on every build. `harness-*.cil` are the one-off experiments that
produced the battery and display fixes, kept here as evidence; the build
does not apply them.

This file is the experiment log. The procedure for a ROM developer who has
to adapt a ROM's policy to a newer kernel is
[ADAPTING-A-ROM-TO-A-NEWER-KERNEL.md](ADAPTING-A-ROM-TO-A-NEWER-KERNEL.md);
the entries below are the evidence behind it.

The vendor partition is read-only and dm-verity protected, so these are the
only way to adjust what the stock vendor policy ends up enforcing without
rebuilding a ROM. Each file's SHA256 is recorded in the matching
`package-run<N>.json` as `policy_append_sha256`, so a run can always be tied
back to the exact text that produced it.

`build-kernel.sh` passes `porting/policy/port-genfs-kgsl.cil` to
`--policy-append` and fails the build unless the package report's
`policy_append_sha256` is that file's SHA256. The packaging tool appends the
bytes to the `userdebug_plat_sepolicy.cil` record and re-parses the cpio it
built, so a fragment that did not land is a build failure, not a boot
surprise.

## port-genfs-kgsl.cil — KGSL attributes for the Power HAL

**Applied by `build-kernel.sh` from this change on; not booted yet.**

One `genfscon` for `/devices/platform/soc@0/1c00000.gpu/kgsl/kgsl-3d0`.
The vendor policy grants `hal_power_default` write on `sysfs_kgsl`, but the
rule's literal 4.19 CAF path no longer matches this kernel, so the
attributes were on the generic `sysfs` type and the writes were denied.
The path is literal, which is a prefix match because
`genfs_seclabel_wildcard` is 0, so the one line covers the whole directory
including the files the graphics, perf and thermal domains read.

The runtime relabel in `scripts/initramfs-diag/init.c` is kept as a
fallback: it reads the directory's label (which the relabel worker itself
never changes) and relabels the files only when the `genfscon` did not
land. A boot with this fragment should log `kgsl sysfs labelled by
policy`; a boot without it still logs the older `kgsl sysfs relabelled`
count.

## harness-genfs.cil — battery/charging power_supply labels

**Used by run141, and it works.** Three `genfscon` statements giving our
power_supply directories the labels `vendor_sepolicy.cil` already grants the
health HAL access to.

Why it is needed: the vendor policy labels those directories with `genfscon`
using **literal CAF 4.19 sysfs paths**, then allows only those types:

    (genfscon sysfs "/devices/platform/soc/200f000.qcom,spmi/spmi-0/spmi0-02/
       200f000.qcom,spmi:qcom,pmi8950@2:qcom,qpnp-smbcharger/power_supply/battery"
       (u object_r sysfs_battery_supply ((s0) (s0))))
    (allow hal_lineage_health_default sysfs_battery_supply (file (...)))   ; vendor_sepolicy.cil:17841

Every path component differs under mainline naming:

| component | vendor (CAF 4.19) | this kernel (6.12) |
|---|---|---|
| root | `platform/soc` | `platform/soc@0` |
| bus | `200f000.qcom,spmi` | `200f000.spmi` |
| slave | `spmi0-02` | `spmi-0/0-02` |
| pmic | `...:qcom,pmi8950@2` | `...:pmic@2` |

So nothing matched, the nodes kept the generic `sysfs` label, the HAL's allow
never applied, `vendor.lineage.health-service` never registered
`IChargingControl`, and SystemServer blocked forever in
`ChargingControlController.waitForDeclaredService`. That was the boot
blocker.

Renaming DT nodes to CAF conventions was rejected: `soc@0` is a prefix of
*every* device path on the board, and the `spmi0-02` component is generated by
`drivers/spmi/spmi.c:473`, not by the DT. Matching it would mean changing the
SPMI core, which risks losing every regulator on the board.

## harness-sysfs-allow.cil — blanket sysfs allows

**Used by run140, and it did NOT work.** Kept only as the record of a failed
experiment. Three `allow ... sysfs (file ...)` statements compiled cleanly
(`secilc exit_code=0x0`) and were then silently ineffective: the health HAL
kept getting the same `tclass=file` denials.

This is why the genfscon route was tried next, and it is the reason to prefer
labelling the right objects over widening access to the wrong ones. Not a
`neverallow`; all 228 `neverallow` rules in `vendor_sepolicy.cil` were checked
and none touch `sysfs`. The reason this file had no effect is **unexplained**.
## A limit worth knowing before writing more genfscon

The ramdisk CIL alone is insufficient to validate a `genfscon` type: init
merges policy from `/system` and `/vendor`. Complete captured inputs can prove
concrete type declarations and attribute mappings.

`sysfs_leds` is a concrete type (`userdebug-run33.cil:2069`) with existing
light HAL grants (`:37345`). `sysfs_leds_202604` is a versioned **attribute**
mapped to that type (`plat_pub_versioned.cil:1231`), not a valid context type.
Using the attribute as run151's label made `secilc` abort:

    secilc: Type not a type or type alias
    secilc: Failed to compile cildb: -1
    init: secilc exit_code=0xff00

Earlier backlight labels targeted the wrong raw SPMI WLED object, not a type
without grants. Run168's `run168-test/sysfs-paths.log` now confirms the MDSS
LED's canonical path:

    /sys/devices/platform/soc@0/1a00000.qcom,mdss_mdp/1a00000.qcom,mdss_mdp:qcom,mdss_fb_primary/leds/lcd-backlight

`harness-genfs-backlight-attrs.cil` labels that directory with concrete
`sysfs_graphics`; the prefix also covers descendants. The captured
`rom-sepolicy-system-a-b9cb6955d584.tar` vendor policy already grants this type
to light HAL (`vendor_sepolicy.cil:7680-7690`), composer (`:7367-7370`),
dpps (`mm-pp-daemon`, `:11573-11576`) and init (`:9821`), including:

    (allow hal_light sysfs_graphics (file (ioctl read write getattr lock append map open watch watch_reads)))
    (allow mm-pp-daemon sysfs_graphics (file (ioctl read write getattr lock append map open watch watch_reads)))
    (allow init_202604 sysfs_graphics (file (setattr)))

This label change has **not been runtime tested**.
