# SD card (mmcblk1) throughput — 2026-10-05

> **Historical record - 2026-10-05.** This is what
> the evidence showed at the time and has not been rewritten. The
> current state is [CURRENT-STATE.md](../../CURRENT-STATE.md).

Measured on the running device with `artifacts/storage/speedtest.sh`, test file
created in `/root` (on `/dev/mmcblk1p2`), caches dropped before reads.

## Device under test

| | |
|---|---|
| Card | `mmcblk1` — "SD32G", CID `744a6053443332473049e426b9010300`, manfid `0x000074`, oemid `0x4a60`, date 03/2016 |
| Size | 29,820 MiB |
| Bus | 200 MHz requested, 199,999,951 Hz actual, 4-bit, 1.80 V, **UHS-I SDR104** (timing spec 6) |
| Filesystem | ext4, 27.7 GiB, mounted rw at `/` (pmos root) |

## Results

| Test | Throughput | Time |
|---|---|---|
| Sequential write, 1 GiB | **9.3 MB/s** | 110.4 s |
| Sequential read, 1 GiB | **78.2 MB/s** | 13.1 s |
| 4 KiB-block write, 64 MiB | **10.5 MB/s** | 6.1 s |
| 4 KiB-block read, 64 MiB | **80.3 MB/s** | 0.8 s |

## Reading

Reads are close to the UHS-I SDR104 ceiling (~104 MB/s theoretical), so the bus
and the card's read path are healthy. **Writes are ~8× slower than reads**,
which is not normal: a card of this class should do 30-70 MB/s sequential
write. In order of likelihood:

1. The card's internal SLC cache is exhausted and it falls back to raw TLC/NAND
   programming speed (10 MB/s class is typical for that state).
2. Aging — the CID says the card was manufactured 03/2016; worn cells force
   read-modify-write and block remapping, which hits exactly this profile.
3. Thermals in the slot, less likely given reads are fine.

Practical consequences for the port: package installs, sysupgrade images and
build artifacts on this card cost roughly 2 minutes per GiB written, while reads
are fine. Expect slow `pacman -S`/`apk add` and avoid doing heavy I/O on the SD
card during benchmarking.
